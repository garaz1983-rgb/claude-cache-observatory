Check your own data

Everything runs locally in your browser: your log files never leave this machine. Nothing is uploaded, and there is nothing to sign up for.

Desktop browser required. The logs live on the machine where Claude Code runs (~/.claude/projects); mobile browsers cannot access them.

Before you run it: what this page does, and what it does not

  • Your log files never leave this machine. Reading, scoring and charting all happen inside this tab, and everything is gone when you close it. Running a check makes zero network requests: open F12 → Network and watch it yourself.
  • Nothing is sent unless you press the button in step 3. Even then, all that leaves is the aggregate numbers shown to you first (daily counts and totals) plus an optional nickname. Conversation text, file paths, session IDs and timestamps are not part of the submission schema at all.
  • There is no build step. The code your browser runs is the same file that sits in the repo, so you can diff view-source against GitHub line by line.
  • No login, no account. The page only reads log files; it never talks to your Anthropic account or the API.
How this site is put together (file map)
  • assets/parse.js — the scoring engine. Every number on this page comes from it. It follows the same rules as the CLI scripts/check_cache_loss.py, and an automated test compares the two outputs.
  • assets/charts.js — drawing only (charts and heatmap). It does no scoring.
  • functions/api/submit.js — the only code that runs on a server. It is called only when you press submit, validates the schema, and commits to the public repo.
  • data/submissions.json — the public dataset. One submission is one commit, so the whole history is auditable by anyone.
  • wrangler.toml — even the server configuration lives in the repo: there is no hidden backend.

How losses are judged (TTL-strict, v2.1)
  • Candidate: a record the server itself stamped with message.diagnostics.cache_miss_reason = previous_message_not_found. Nothing is inferred.
  • In-TTL loss: the idle gap to the previous request in the same session file is under 30 minutes (main session) or 5 minutes (subagent). Longer gaps are legitimate TTL expiries and are not counted.
  • Iron loss: idle gap under 5 minutes, meaning no published TTL could have expired the cache.
  • Dedup: one event per requestId; a later record of the same request may only back-fill a missing reason.
  • Cost: the re-billed cost of a loss is that request's cache_creation_input_tokens.
